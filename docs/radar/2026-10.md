## Talked about (last 30 days)

### 1. `@vitest/browser-playwright` — real-browser component tests (Vitest + Playwright)

**Why it came up:** Vitest 5 shipped **2026-09-03** with faster Browser Mode, and the Trace View guide was refreshed **2026-09-28** ([Vitest 5 announcement](https://vitest.dev/blog/vitest-5), [Trace View](https://vitest.dev/guide/browser/trace-view)). Maintainers recommend the Playwright provider when you already run Playwright ([browser mode guide](https://vitest.dev/guide/browser/)). Recent Q&A (e.g. [vitest-dev/vitest#11056](https://github.com/vitest-dev/vitest/discussions/11056), follow-ups through **2026-09-06**) covers how browser-mode auth differs from Playwright’s `storageState` pattern.

**Current repo touchpoints:**

| File | Role |
|------|------|
| `modern/vitest.config.ts` | `environment: "jsdom"` for unit/component tests |
| `modern/playwright.config.ts` | Full E2E against `next start` |
| `modern/package.json` | `vitest@^5.0.3`, `@playwright/test@^1.63.0` (no `@vitest/browser-playwright` yet) |
| `modern/src/**/*.test.tsx` | RTL + jsdom (nav, breadcrumbs, data utilities) |

**Possible next step:** Add `@vitest/browser-playwright`, enable `test.browser` for a **small** subset of tests that need layout/DOM APIs jsdom fakes poorly (nav canvas, GSAP-driven DOM). Keep Playwright E2E for locale routing and full flows. Optional: `browser.traceView` for CI HTML reports on flaky UI tests.

**Migration sketch:**

1. `npm install -D @vitest/browser-playwright` (align with existing `playwright` / `@playwright/test` versions).
2. Extend `vitest.config.ts` with a `test.projects` split: default jsdom project unchanged; browser project with `provider: playwright()` and `instances: [{ browser: 'chromium' }]`.
3. Move or duplicate 1–2 high-value component tests into the browser project; run `vitest run --project browser` in CI only if runtime cost is acceptable.
4. Document when to use browser vs jsdom vs E2E in `modern/AGENTS.md`.

**What can break:** Slower CI; browser-mode tests run **inside** the browser (different from Playwright test runner); GSAP tests may need real `requestAnimationFrame` timing adjustments; parallel file isolation differs from Playwright E2E.

**Worth doing now?** **Later / incremental.** jsdom coverage is healthy today. Revisit when a test is blocked by jsdom limitations or when consolidating Playwright install maintenance is worth the config split.

### 2. Lingui 6 — compile-time i18n alternative (next-intl stack)

**Why it came up:** **Lingui v6.8.0** released **2026-09-23** ([release notes](https://github.com/lingui/js-lingui/releases/tag/v6.8.0)). Docs and agent skills were updated for **Next.js 16** (proxy rename, Turbopack, `next/root-params`) ([RSC tutorial](https://lingui.dev/tutorials/react-rsc), [Next App Router setup](https://github.com/lingui/skills/blob/main/skills/lingui-framework-setup/references/nextjs-app-router.md)). Comparison write-ups still position Lingui as the main “bundle/runtime lean” alternative to next-intl on App Router ([Wellworn i18n verdict](https://wellworn.dev/verdicts/i18n-nextjs) — Lingui 6 vs next-intl 4.14).

**Current repo touchpoints:**

| File | Role |
|------|------|
| `modern/src/middleware.ts` | next-intl middleware |
| `modern/src/i18n/request.ts`, `modern/src/routing.ts` | next-intl routing + request config |
| `modern/src/navigation.ts` | Typed locale-aware navigation |
| `modern/src/messages/*.json` | Static JSON catalogs (en, es) |
| `modern/next.config.ts` | `next-intl/plugin` |

**Possible next step:** Not a recommended swap for this portfolio: two locales, JSON in git, and next-intl already owns middleware, metadata, and `Link` helpers. Lingui is worth knowing if you add **extracted** PO workflows, shared packages outside Next, or strict bundle budgets on client islands.

**Migration sketch (if ever needed):**

1. Replace middleware with Next 16 `proxy.ts` + locale prefix routing per Lingui tutorial.
2. Pin `@lingui/swc-plugin` to exact version for Next 16.3.8 ([plugins.swc.rs](https://plugins.swc.rs)).
3. Add `lingui compile` before dev/build; migrate `messages/*.json` to PO or compiled catalogs.
4. Replace `NextIntlClientProvider` / `useTranslations` with `setI18n` + `@lingui/react/macro` patterns in every layout/page that renders copy.

**What can break:** SEO URLs, hreflang, static generation (`setRequestLocale` equivalents), Flash popup locale query params, and every colocated test that imports messages.

**Worth doing now?** **No.** next-intl 4.14.9 is active (published **2026-10-02**). Stay on next-intl; consider Lingui only for a greenfield app or a monorepo package shared with non-Next consumers.

## Stale

### `vercel` CLI (devDependency) — advisories without a fix on current majors

**Package:** `vercel@^62.2.0` in `modern/package.json` (lockfile **62.2.0**; npm latest **63.1.0** as of scan).

**Signal:** `npm audit` in `modern/` reports **36** vulnerabilities (including **critical** `tar` via `@vercel/container`). For both **62.2.0** and a clean install of **63.1.0**, `npm audit` offers **no upgrade path** on the current line — only `npm audit fix --force`, which **downgrades** to `vercel@54.17.3` (breaking). That matches the radar rule: **security advisories with no patched release** on the version line you would install.

**Affected usage:** Local/preview deploy only (`npm run deploy` / `deploy:prod` in `modern/package.json`). Production runtime on Vercel does not bundle this CLI.

**Links:**

- [GHSA-vmf3-w455-68vh](https://github.com/advisories/GHSA-vmf3-w455-68vh) (tar — critical, among others in audit output)
- [GHSA-x8mw-p69m-v3mx](https://github.com/advisories/GHSA-x8mw-p69m-v3mx) (@fastify/busboy via `undici` / `@vercel/node`)

**Mitigation options (no code change required in app):**

1. **Track upstream:** Watch [vercel/vercel](https://github.com/vercel/vercel) releases; bump CLI when audit clears without a forced downgrade.
2. **Reduce exposure:** Prefer Vercel Git integration for production deploys; use CLI only on trusted maintainer machines.
3. **Do not** blindly `npm audit fix --force` in `modern/` — it pins an obsolete CLI major.

**What can break:** Nothing in the Next app itself; only local deploy tooling and CI if you add CLI-based deploy steps later.

**Worth doing now?** **Monitor.** Flagged for visibility, not an emergency for a static/SSR portfolio deployed via Git. Re-check monthly; Dependabot will propose semver bumps separately.
