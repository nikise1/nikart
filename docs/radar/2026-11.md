## Talked about (last 30 days)

### 1. `vitest-plugin-rsc` — App Router tests inside Vitest Browser Mode (Vitest + Next.js)

**Why it came up:** **v0.3.0** shipped **2026-10-08** with a breaking redesign: Next’s own request handler, renderer, and router run beside the test in the browser ([release v0.3.0](https://github.com/storybookjs/vitest-plugin-rsc/releases/tag/v0.3.0), merged in [PR #57](https://github.com/storybookjs/vitest-plugin-rsc/pull/57)). **v0.4.0-alpha.0** followed **2026-10-22**. Maintainers document Next **16.4+**, Vitest **5.0.3+**, Vite **8**, and `@next/routing` pinned to the same version as `next` ([README](https://github.com/storybookjs/vitest-plugin-rsc/blob/main/README.md)). This is the natural “next step” after generic Vitest Browser Mode (`@vitest/browser-playwright`) for teams that hit the Next.js docs caveat that Vitest does not support async Server Components ([Next.js Vitest guide](https://nextjs.org/docs/app/guides/testing/vitest)).

**Current repo touchpoints:**

| File | Role |
|------|------|
| `www-root/vitest.config.ts` | `environment: "jsdom"`; no browser project |
| `www-root/playwright.config.ts` | Full E2E via `next build && next start` |
| `www-root/package.json` | `next@16.4.2`, `vitest@^5.0.5`, `@playwright/test@^1.64.1` — no `vitest-plugin-rsc` or `@vitest/browser-playwright` |
| `www-root/src/app/[locale]/layout.tsx`, `page.tsx`, `[...path]/page.tsx` | App Router + next-intl; mostly Server Components |
| `www-root/src/**/*.test.tsx` | RTL + jsdom (nav, breadcrumbs, slideshow, data) |

**Possible next step:** Pilot **one** browser-mode test file that opens a real locale route (e.g. `/en`) with `renderServer({ url })` from `vitest-plugin-rsc/nextjs/testing-library`, asserting hydrated client UI (nav shell). Keep existing jsdom tests and Playwright E2E unchanged until the pilot proves stable CI time.

**Migration sketch:**

1. `npm install -D vitest-plugin-rsc @vitest/browser-playwright` and `npm install -D @next/routing@$(node -p "require('next/package.json').version")`.
2. Add a second Vitest project (or split config): browser project with `vitestPluginRSC()`, `vitestPluginNext()`, `provider: playwright()`, `instances: [{ browser: 'chromium' }]`.
3. Point `vitestPluginNext()` at the app root; ensure Turbopack/root imports for `content/json/data.json` still resolve (same constraint as `next.config.ts` today).
4. Write 1–2 tests using `page` / `within(document.body)` instead of RTL `screen` while a route is open (plugin docs warn `screen` does not see the page body).
5. Run browser project in CI only if runtime is acceptable; document jsdom vs browser vs E2E in `www-root/AGENTS.md`.

**What can break:** Slower tests; Next internal coupling (plugin tracks `next@16.4.0`, `latest`, `canary` in CI); next-intl middleware/locale prefixes must match `url`; GSAP-heavy components may need real `requestAnimationFrame` timing; duplicate coverage with Playwright if scope creeps.

**Worth doing now?** **Later / experimental.** jsdom + Playwright already cover this portfolio. Revisit when you want faster feedback than full E2E for a specific App Router + RSC route, or when Next documents this pattern officially.

### 2. `motion` (`motion/react`) — declarative React UI motion alongside GSAP

**Why it came up:** Several **October 2026** write-ups revisit GSAP vs Motion (formerly Framer Motion) for Next.js App Router: scroll/timeline work stays on GSAP; state-driven UI (modals, lists, `AnimatePresence`, layout) is where Motion is discussed as a **complement**, not a replacement ([Nabe, Oct 13 / updated Oct 29](https://nabe.pro/insights/gsap-vs-framer-motion), [Motion docs — GSAP vs Motion](https://motion.dev/docs/gsap-vs-motion), [Jack Miao — GSAP in React/Next, Oct 5](https://jackyangmiao.com/blog/gsap-react-nextjs-guide)). GSAP 3.13+ made plugins free, which renewed “when do I still reach for Motion?” threads.

**Current repo touchpoints:**

| File | Role |
|------|------|
| `www-root/src/lib/gsap.ts` | `useGSAP`, `ScrollTrigger` registration |
| `www-root/src/lib/nav-animations.ts`, `use-nav-animator.ts`, `use-breadcrumb-animator.ts` | GSAP timelines for nav/breadcrumbs |
| `www-root/src/components/thumbnail/*`, `slideshow/slideshow.tsx` | GSAP-driven grid and slideshow |
| `www-root/package.json` | `gsap@^3.15.0`, `@gsap/react@^2.1.2` — no `motion` package |

**Possible next step:** **Do not replace GSAP** on this site (scroll-linked nav and legacy-faithful motion are GSAP-shaped). If a future UI needs enter/exit on a small client island (e.g. a modal or toast), add `motion` only there rather than rewriting breadcrumb/notch timelines.

**Migration sketch (hypothetical island only):**

1. `npm install motion` and import from `motion/react` in a dedicated `'use client'` wrapper.
2. Keep GSAP scopes separate; avoid animating the same DOM nodes with both libraries.
3. Match reduced-motion preferences already implied by legacy behavior.

**What can break:** Bundle size (+~30–50 KB gzipped depending on imports); two animation runtimes on one element; hydration mismatches if server markup does not match initial motion props.

**Worth doing now?** **No.** Current GSAP coverage matches the migration goal (reproduce legacy motion). Motion is worth knowing for **new** React-state UI, not this radar cycle.

## Stale

### `vercel` CLI (devDependency) — advisories with no clean fix on current majors

**Package:** `vercel@^65.2.0` in `www-root/package.json` (lockfile **65.2.0**; npm latest **65.9.0** as of scan).

**Signal:** `npm audit` in `www-root/` reports **41** vulnerabilities (**1 critical**, e.g. `tar` transitively). A clean install of **65.9.0** still reports **41** vulnerabilities with the same guidance: `npm audit fix --force` **downgrades** the CLI to an obsolete major (e.g. **53.x**), not a patched current line. Nested `zod` inside `@vercel/*` packages triggers [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) without an in-range fix. This matches the radar rule: **security advisories with no patched release** on the version line you would install.

**Affected usage:** Local/preview deploy only (`npm run deploy` / `deploy:prod`). Production on Vercel does not bundle this CLI.

**Links:**

- [GHSA-vmf3-w455-68vh](https://github.com/advisories/GHSA-vmf3-w455-68vh) (`tar` — critical in audit tree)
- [GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5) (nested `zod` in Vercel CLI deps)
- [vercel/vercel releases](https://github.com/vercel/vercel/releases)

**Mitigation options (no app code change):**

1. Prefer **Git-based deploys** for production; treat CLI as maintainer-only tooling on trusted machines.
2. **Track upstream** CLI releases; bump when audit clears without `--force`.
3. **Do not** run `npm audit fix --force` in `www-root/` — it pins an obsolete CLI.

**What can break:** Nothing in the Next app; only local deploy workflows.

**Worth doing now?** **Monitor** (same as October radar). Dependabot may still propose semver CLI bumps separately; those are not staleness by themselves.
